# ADR-0002: Build the first Director slice on the verified Paseo 0.7.2 public subset

- **Status:** Accepted
- **Date:** 2026-09-06
- **Beads Task:** `dir-m0.1`
- **Plan gate:** M0 Paseo API surface
- **Decision owner:** `dir-m0.1` Task owner

## Context

Director needs native cross-client UI, a trusted daemon-side engine, schema-validated UI/engine calls, provider discovery, session-scoped MCP configuration, and durable correlation with native Paseo agents and execution workspaces. The Paseo plugin API is experimental, the upcoming v0.8 entry layout is incompatible with v0.7, and deployed documentation can move ahead of published npm artifacts.

The plan forbids undocumented endpoints, direct writes to Paseo's internal database, UI automation as infrastructure, and log parsing as a source of truth. M1 cannot begin unless its smallest vertical slice has a public supported path.

## Question or hypothesis

Can the Director M1 walking skeleton be implemented against the installed stable Paseo public plugin and SDK APIs without private endpoints, direct internal database access, or UI automation?

## Acceptance criteria

- Capture exact available versions, operating system, and headless topology without inferring missing values.
- Inventory the public Project, Workspace, Agent, provider, configuration, event, plugin RPC, MCP, and UI surfaces Director requires.
- Exercise the official scaffold and representative authenticated read-only operations against the installed daemon.
- Record capability flags, missing surfaces, version skew, compatibility bounds, and reproducible commands.
- Select a public M1 path or keep M1 blocked.

## Evidence

The full sanitized transcript and compile-time contract probe are in:

- [Paseo 0.7.2 public-surface evidence](../evidence/m0.1/paseo-0.7.2-public-surface.md)
- [Published API contract probe](../evidence/m0.1/api-contract-probe.ts)

Key facts:

- `0.7.2` was the installed CLI version, official download version, and npm `latest` version for the plugin/client/protocol artifacts on 2026-09-06.
- The official `paseo plugin init` scaffold pinned `@getpaseo/plugin` to exact `0.7.2`; dependency installation and strict typechecking passed.
- The v0.7 public plugin surface contains every UI and RPC primitive required for the M1 Board/List and engine boundary.
- The public SDK contains Project/Workspace/Agent/provider/configuration roots, handle recovery, agent labels, subscriptions, session-scoped MCP input, provider/model/mode/thinking discovery, and archive-based runtime closure needed to proceed to lifecycle proof.
- Authenticated injected MCP calls observed the installed daemon, and one Codex session reported `supportsMcpServers: true`; the full provider proof remains `dir-m0.3`.
- The public status response returned `daemonVersion: null`, and the plugin API has no public host-version/feature accessor or manifest compatibility range.
- Current documentation and `main` describe additions absent from the immutable published `0.7.2` declarations. Those additions are not part of this decision.

## Alternatives considered

### Follow deployed documentation and Paseo main

Rejected. It would compile Director against methods or entry layouts not present in the stable artifact installed by users. The observed v0.7 documentation/package skew makes unversioned docs insufficient as a compatibility contract.

### Depend on internal protocol exports or private daemon RPCs

Rejected. Some missing operations exist in low-level internal exports, CLI commands, or agent MCP, but those are not methods on the public `PaseoApi` supplied to plugin handlers. This would violate the plan and couple the engine to unstable authority paths.

### Wait for v0.8 before implementation

Rejected for M1. Stable v0.7.2 already provides the minimal public UI/RPC/SDK subset. v0.8 remains preview, has a deliberately incompatible entry layout, and requires its own evidence before adoption.

### Build against the immutable v0.7.2 subset and fail closed

Selected. It minimizes the adapter surface, permits the fake-agent walking skeleton, and leaves real lifecycle and provider behavior behind existing M0 gates.

## Decision

**Go**, with a narrow compatibility boundary.

The M1 scaffold may target the immutable published `@getpaseo/plugin@0.7.2` contract and only operations positively listed in the evidence. This decision does not authorize M1 by itself: every remaining M0 Task and the independent M0 exit gate still apply.

Director will:

1. pin the Paseo plugin package to exact `0.7.2` and commit the dependency lockfile;
2. keep every Paseo call behind a thin adapter;
3. structurally verify required methods at engine startup and stop with a precise diagnostic when the host lacks them;
4. persist native workspace and agent IDs plus Director correlation labels before subsequent effects;
5. reconcile with `list`, `ref`, and `refresh` after startup, using subscriptions only as wake-up signals;
6. use the Organizer repository and selected TaskStore for durable state, never plugin/browser storage;
7. exclude documentation-only methods such as permission response and timeline append until a later stable artifact declares and proves them;
8. treat built-in agent MCP as an agent capability, not an engine backdoor;
9. treat `agent.archive()` as only a candidate termination mechanism until `dir-m0.2` proves its lifecycle semantics;
10. ship no v0.8 compatibility entry in the v0.7 line.

The initially supported host is exact stable `0.7.2`. A later `0.7.x` host is not admitted merely because its semver is in range; it must pass the same generated-scaffold, type-contract, lifecycle, and runtime capability suite. v0.8 requires a separate migration decision and release line while its incompatible entry model remains in preview.

Backend code must also remain within the SDK's documented Node.js 22-or-newer baseline and the generated ES2020 compiler target. The observed Node.js 26.7.0 runtime does not authorize Node.js 26-only APIs.

## Consequences

- M1 has a supported public path for its UI/RPC boundary and fake-agent vertical slice.
- `dir-m0.2` must install a disposable exact-0.7.2 plugin and prove creation, observation, archive/interruption, reload, crash, daemon restart, subscriptions, correlation, and recovery. Failure keeps M1 blocked and selects a scope reduction or upstream request.
- `dir-m0.3` must prove session-scoped custom MCP and tool policy independently for each admitted provider. The single observed Codex result cannot be generalized.
- Director cannot promise automatic permission responses, daemon-pushed timeline rows, hard agent deletion, or dynamic post-creation settings on the stable SDK.
- Lack of a public daemon version and compatibility manifest requires fail-closed structural probes and explicit tested-host documentation.
- Documentation drift becomes a regression input: CI must compile contract probes against every explicitly supported Paseo artifact rather than scrape `main`.
- Windows and additional Linux topology behavior remain owned by later M0 platform and lifecycle Tasks.

## Independent verification

The independent reviewer must reproduce the scaffold/type probe and inspect this decision at one exact Candidate SHA. The exact SHA and verdict are recorded in `dir-m0.1` rather than embedded here, because changing this file after review would create a different unreviewed Candidate.
